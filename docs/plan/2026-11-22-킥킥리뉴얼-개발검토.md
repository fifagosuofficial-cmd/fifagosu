## 0. 결론 요약

1. 필수 범위는 **조금 줄이면 오늘 안에 됩니다.** 대신 이름 생성기 문구(약 200줄)가 일정의 절반을 차지해요. 태그를 12개에서 8개로 줄이고, 글자 매칭 방식을 바꾸는 걸 제안해요.
2. **결과 링크의 og:title 넣기(Pages Functions)는 "다음"이 아니라 오늘 넣자**고 주장해요. 카톡 링크 미리보기에 결과가 안 보이면 "너는 뭐 나와?" 루프의 절반이 빠져요. 코드는 약 60줄, 1시간이에요. 단, `functions/` 구조가 바뀌니 **대표 승인을 지금 받아야** 오늘 범위에 넣을 수 있어요.
3. 결과 링크는 `/fun/?r=…` 말고 **`/fun/r/?d=…`(경로 접두사 + 짧게 인코딩한 묶음 1개)**를 추천해요.
4. 옛 링크는 리다이렉트보다 **"허브에서만 내리고 해시 링크는 계속 열리게"** 두는 게 더 싸고 안전해요(`number`만 `name`으로 넘김).
5. 가장 큰 위험은 **main에 합치는 순간이 곧 배포**라는 점이에요. `news.yml`이 하루 4번 main을 자동 배포해요.

### 1-2. 빼거나 단순화할 것
- **[수정제안] 허브 히어로 카드 안의 이름 입력창 → 빼기.** 큰 타일(`#/name`)로만 둬요. 입력창을 허브에 넣으면 introView와 이중 구현이 돼요. 효과 차이는 탭 1번이에요.
- **[수정제안] duo "문구 풀 전면 교체" → "낡은 밈 삭제 + TIER당 1~2개 보강"으로 축소.** 바이럴에 중요한 건 문구보다 "나랑도 궁합 보기" 결과 링크예요. 링크가 필수, 문구는 최소한으로.
- **[수정제안] ifplayer 코멘트 1~2줄 컷 → 문구를 다시 쓰지 말고 코드로 첫 문장만 잘라 쓰기**(`split(/(?<=[.!?])\s/)[0]`). CM 데이터 16KB를 손으로 고칠 시간이 없어요.
- **[동의] 별명 바꾸기, price/club/fan 문구는 "있으면 좋음"으로 유지.**
- **[수정제안] balance**는 대머리 문항 1개만 교체(외모 소재는 그것 하나예요).

### 1-3. 쉬운데 효과 큰 것: 오늘 넣자고 주장
- **Pages Functions og 주입 (오늘 필수로 올리자).**
  - 근거 ① 카톡 크롤러는 JS를 실행하지 않아요. 정적 방식이면 친구 결과 링크를 보내도 미리보기는 항상 "킥킥 · 내 이름으로 만드는 축구 별명"이에요. 결과가 보여야 "윤재 뭐 나왔는데?" 하고 누르게 돼요.
  - 근거 ② 작업량이 작아요. `functions/fun/r/index.js` 한 파일에서 `env.ASSETS.fetch('/fun/')`로 기존 HTML을 읽고, `HTMLRewriter`로 `og:title`/`og:description`/`og:url`만 바꾸고, `<base href="/fun/">`를 넣으면 끝이에요. 별명 계산 로직은 Function에 안 넣고, **클라이언트가 결과 링크를 만들 때 별명 텍스트를 같이 넣는 방식**(2-3)이면 서버에 생성 로직을 복제할 필요가 없어요.
  - 근거 ③ 무료이고 한도에 영향이 작아요. Pages는 `functions/` 폴더를 보고 실행 경로를 자동으로 정해요(`/api/*`, `/fun/r/*`만 Functions가 돌고 나머지 정적 파일은 한도에 안 잡혀요). 그래서 `_routes.json`은 따로 안 만들어도 돼요. 요청 수는 "링크 미리보기 1회 + 클릭 수"뿐이라 하루 10만 건 한도에서 넥슨 API 중계와 함께 써도 여유 있어요.
  - 근거 ④ 배포 파이프라인이 이미 `cp -r functions dist/`를 하고 있어서(crawl.yml 86줄, news.yml 60줄) 워크플로를 고칠 필요가 없어요.
  - 조건: `functions/` 구조가 바뀌는 일이라 **대표 승인(초안 ⑦-3)을 지금 받아야** 해요. 승인이 안 나도 2번 형식이면 Function 없이도 결과 링크는 작동하게 만들 수 있어요(아래 2-2의 대비책).
- **결과 링크 복사 버튼의 인앱 브라우저 대비**: 카톡 인앱 브라우저는 `navigator.share`와 `clipboard`가 막히는 경우가 있어요. 복사가 실패하면 **링크가 선택된 입력창을 띄우는 대비책**을 넣어요(10분, 효과 큼).

## 2. 결과 링크 형식

### 2-1. 쿼리(`/fun/?r=`) vs 경로(`/fun/r/…`)
**[수정제안] `/fun/r/?d=<인코딩한 묶음>`을 추천해요.** 경로 접두사와 쿼리 1개를 섞은 형태예요.

| 기준 | `/fun/?r=name&n=..&a=..` (초안) | `/fun/r/?d=..` (제안) |
|---|---|---|
| Function 실행 범위 | `/fun/` 자체에 Function을 걸어야 해서 **허브 방문까지 전부 Function이 실행**돼요(한도 낭비, 장애 시 허브까지 영향) | `/fun/r/*`만 실행. 허브는 계속 순수 정적 |
| 장애 영향 | Function 오류 = 킥킥 전체가 안 열림 | 결과 링크만 영향 |
| 상대 경로 | 문제없음 | `fun/index.html`의 `../index.html`, `../site/brand/...` 상대 경로가 `/fun/r/`에서는 깨져요. → Function이 `<base href="/fun/">`를 넣으면 해결 |
| 해시 라우팅 | 쿼리와 해시가 같이 있으면 우선순위 규칙이 필요 | 같음(아래 2-4) |

- 순수 경로형(`/fun/r/name/윤재/2130…`)은 슬래시와 한글 처리가 번거로워서 비추천이에요. 쿼리 1개가 파싱하기 가장 쉬워요.

### 2-2. Function 승인이 안 나면 (대비책)
- `fun/r/index.html`을 정적 파일로 하나 두면 돼요. 내용은 `location.replace('/fun/'+location.search)`만 하는 몇 줄짜리 HTML이에요. 링크 형식은 그대로 두고, 나중에 Function을 붙이면 같은 링크가 바로 미리보기까지 지원돼요. **오늘 뿌린 링크가 나중에도 그대로 살아 있어요.**
- 참고: Function이 있으면 같은 경로의 정적 파일보다 Function이 먼저 실행돼요. 그래서 둘 다 둬도 충돌하지 않아요.

### 2-3. 묶음(`d`) 내용과 인코딩
- **[수정제안] 이름 평문 대신 base64url로 묶기.** `d = base64url(JSON 또는 '|' 구분 문자열)`.
  - 예: `v1|name|윤재|2130021130|후반 윤재투입` → 약 50자.
  - 들어가는 것: 형식 버전(`v1`), 콘텐츠 id, 이름, 답변 코드, **별명 텍스트(미리보기용)**.
  - 근거 ① 한글 쿼리는 퍼센트 인코딩되면 `%EC%9C%A4…`처럼 3배로 길어져요. 메신저에 따라 한글 URL을 중간에서 자르는 경우도 있어요. base64url은 영문·숫자만 써서 안전해요.
  - 근거 ② 별명 텍스트를 같이 넣어 두면 Function은 **디코딩해서 og:title에 꽂기만** 하면 돼요. 생성 로직을 서버에 복제하지 않아도 돼요. 클라이언트는 이 텍스트를 믿지 않고 이름+답변으로 다시 계산해서 보여줘요(조작해도 친구 화면엔 진짜 결과가 떠요).
  - 근거 ③ `v1`이 있어야 나중에 질문·문구를 고쳐도 옛 링크를 처리할 수 있어요. 버전이 다르면 옛 링크는 "결과 카드 대신 별명 텍스트만 보여주고 '나도 해보기'"로 대체하면 돼요.
  - **주의(정직하게)**: base64는 암호화가 아니에요. 누구나 풀 수 있고, 어차피 og:title("윤재의 축구 별명…")에 이름이 보여요. 개인정보 보호 수단이라기보다 **"URL이 짧고 깔끔해지는" 효과**예요. 대표 결정 ⑦-5에는 "이름은 미리보기 제목에도 보인다"는 걸 같이 알려야 해요.
- 궁합: `v1|duo|윤재|민수`, 유형형: `v1|manager|bus`.
- 검증: 이름 6자 이하, 답변 코드 길이 = 문항 수, 각 자리 0~3. 하나라도 어긋나면 허브로 보내요.

### 2-4. 해시 라우팅과의 충돌
- `route()` 우선순위: **① `location.search`에 `d`가 있으면 결과 보기 → ② 해시 → ③ 허브.**
- 친구가 결과 화면에서 "나도 해보기"를 누르면 해시만 바꾸면 안 돼요. 쿼리가 남아서 계속 결과 화면이 떠요. → `location.href='/fun/#/name'`로 이동하거나 `history.replaceState`로 쿼리를 지워야 해요.
- `<base href="/fun/">`가 들어간 상태에서 `href="#/"`는 `/fun/#/`로 이동해요(허브로 감). 원하는 동작이라 괜찮아요.
- **버그 포인트**: `SHARE_URL`이 `location.pathname`으로 만들어져서(2564줄) `/fun/r/`에서 열면 카드 하단 주소가 `fifagosu.pages.dev/fun/r`로 찍혀요. → `https://fifagosu.pages.dev/fun/`로 고정해야 해요.

## 3. 이름 생성기 규칙 검토

### 3-1. 이름 처리(성 떼기)
- **[동의]** 성씨 60개 + 복성 7개 + 2글자는 그대로 + 영문은 상황형. 구현 20분이면 돼요.
- **[수정제안]** 2글자 입력 중 "김산"처럼 외자인 경우 "산"만 쓸지 애매해요. 초안대로 그대로 두는 게 맞아요. "OO(으)로 불러요" 표시는 좋은 장치라 유지해요.

### 3-2. 태그 12개 → **[수정제안] 8개로 줄이기**
초안 질문표에서 태그가 나오는 횟수를 세어 봤어요(선택지 40개 기준).

| 태그 | 칼같음 | 핑계 | 대충 | 수다 | 해축 | 지각 | 승부욕 | 주인공 | 읽씹 | 체력 | 야식 | 지갑 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 등장 수 | 6 | 5 | 5 | 4 | 4 | 3 | 3 | 3 | 2 | 2 | 2 | 2 |

- 근거 ① **쏠림**: 칼같음은 6번(1번 문항에는 A·B 둘 다), 읽씹·체력·야식·지갑은 2번뿐이에요. 랜덤으로 답하면 칼같음·핑계·대충이 1위를 거의 독차지하고, **예시 1번 "윤재(지각·체력)"처럼 체력이 2위가 되는 경우는 드물어요.** 수식어 36개를 써 놔도 절반은 거의 안 나와요.
- 근거 ② **동점 투성이**: 답 10개를 12개 태그에 나누면 1위가 2표인 경우가 흔해요. 그러면 시드 랜덤으로 정해져서 "내 답이랑 상관없네"라는 느낌이 다시 생겨요.
- 제안: **8개**(지각, 칼같음, 수다, 읽씹, 해축, 방전(체력), 승부욕, 주인공) + 야식·지갑·핑계는 **근거 조각과 칩에만** 써요. 선택지 40개 = 태그 8개 × 5회로 정확히 균형을 맞춰요. 문구량도 수식어 36→24, 근거 24→16으로 줄어요.
- 대안(12개 유지 시): 태그마다 정확히 3~4회 나오게 질문표를 다시 짜야 해요. 문구량이 그대로라 오늘은 무리예요.

### 3-3. 글자형(글자 사전 + 태그 일치) → **[수정제안] "이름 합성형"으로 바꾸기**
초안 방식은 "이름 끝 글자로 시작하는 단어 중 T1·T2와 태그가 맞는 것"이에요. 두 가지 문제가 있어요.

- 문제 ① **적중률이 낮아요.** 사전 30글자에 한국 이름에 흔한 끝 글자 서·은·아·혁·율·린·성·석·지가 없어요. 그 위에 태그 일치 조건까지 걸면(글자당 단어 1~3개, 태그 2개 맞을 확률) 대략 **10명 중 2~3명만 글자형**이 나오고 나머지는 상황형이 될 것 같아요(추정치, 구현 후 이름 100개로 측정 필요).
- 문제 ② **연결이 안 보여요.** "연속골 세리머니 서연", "도움왕 도윤"은 근거 줄에 "'연'"이라고 적어 줘야 겨우 알아요. 보는 사람 눈에는 그냥 "수식어 + 이름"이에요.

**대안: 이름 끝 글자를 축구 단어 첫 글자와 겹쳐 붙이는 합성(끝말 합성)**
| 이름 | 겹치는 단어 | 합성 결과 | 별명 예시 (수식어는 답변 T1) |
|---|---|---|---|
| 윤재 | 재투입 | **윤재투입** | 후반 12분 윤재투입 (지각) |
| 민수 | 수문장 | **민수문장** | 약속은 막는 민수문장 (칼같음) |
| 서연 | 연장전 | **서연장전** | 답장은 서연장전 가서 (읽씹) |
| 지훈 | 훈련 | **지훈련 불참** | 사유서 완비 지훈련 불참 (핑계 칩) |
| 한경 | 경고 | **한경고 누적** | 단톡방 한경고 누적 (수다) |
| 민준 | 준결승 | **민준결승** | 한 판 더 민준결승 (승부욕) |
| 하은 | 은퇴 | **하은퇴식** | 전반 15분 하은퇴식 (방전) |
| 민석 | 석패 | **민석패** | 이길 때까지 민석패 금지 (승부욕) |
| 지영 | 영입 | **지영입 1순위** | 굿즈 앞 지영입 1순위 (지갑 칩) |
| 도윤 | (윤 단어 없음) | → 상황형 | 단톡 공지 담당 도윤 |

- 근거: 이름이 단어 속에 녹아 있어서 **보자마자 말장난인 게 보여요.** "윤재 델 졸리노"와 달리 이름 글자를 실제로 쓰고, "재투입 윤재"보다 한 단계 더 붙어 있어서 재밌어요. 수식어(답변 기반)가 붙어서 같은 이름이라도 답에 따라 결과가 달라져요.
- **태그 일치 조건은 빼요**(합성 단어는 글자로만 고르고, 답변은 수식어·근거·칩이 맡아요). 그러면 적중률이 사전 범위만큼 올라가요.
- 문구량: 흔한 끝 글자 **40개 × 단어 1~2개 = 약 60개**. 흔한 끝 글자 순위(준·민·서·윤·우·진·현·연·훈·영·호·수·은·아·원·희·지·혁·빈·경·석·성·재·율·린·하·주·찬·태·규·환·철·용·숙·정·희·나·람·솔·온)를 먼저 채우면 대부분 이름을 커버해요. 첫 글자 대비책은 빼요(합성이 안 되니까).
- 위험: 합성이 어색한 경우("민수비수"처럼 같은 소리 반복, 부정적 단어 "은퇴") → 단어마다 검수 필요. 금지 단어 목록(퇴장·부상·강등 같은 부정어는 자조로 웃길 때만)은 QA 체크에 넣어요.

## 4. 콘텐츠 정예화와 옛 링크

- **[동의] number → 이름 생성기로 흡수.** `#/number`로 들어오면 `#/name`으로 넘겨요(`route()`에 별칭 표 `{number:'name'}` 한 줄).
- **[수정제안] league·nation은 "삭제"가 아니라 "허브에서만 내리기".**
  - 근거 ① 해시(`#/league`)는 서버로 오지 않아서 리다이렉트도 결국 클라이언트 코드예요. 코드를 남겨 두면 **옛 링크가 그대로 열리니 리다이렉트를 만들 필요도, 빈 화면이 될 위험도 없어요.**
  - 근거 ② league 등급표 카드는 시각적으로 완성도가 높아요. 나중에 "풋살러 전용" 같은 섹션에서 다시 쓸 수 있어요.
  - 근거 ③ 용량 절감은 league 약 6KB 정도라 의미가 없어요(큰 건 선수 데이터 120KB).
  - 대신 결과 화면 아래 "다른 테스트도 해보기"(`sampleN(APPS…)`)에 숨긴 콘텐츠가 뜨지 않도록 `hidden:true` 표시를 두고 걸러야 해요.
- **[수정제안] ifplayer 20문항 → 12문항은 14문항으로.** 근거: `pickQuestions()`는 12가지 성향을 최소 1번씩 묻게 짜여 있어요(2306–2310줄). 성향 질문 10개 + 포지션 + 주발 = 12문항이면 성향 2개는 질문이 없어서 기본값 3으로 처리돼요. 그러면 닮은 선수 결과가 평균 쪽으로 몰려요. **성향 12개 + 포지션 + 주발 = 14문항**이면 질문 한 줄(`out.length>=18` → `>=12`)만 바꾸면 돼요.

## 5. og:image 제작과 저장 위치

- **[동의] `fun/og/default.png` (1200×630).** `build.py`의 COPY에 `("fun","fun")`이 있어서 `/fun/og/default.png`로 그대로 배포돼요.
- **제작 방법 [수정제안]**: 기존 캔버스 함수(`drawPattern`, `txt`)를 쓰는 작은 HTML을 `tools/build-fun/og.html`로 만들고, Playwright로 열어서 PNG를 저장하는 스크립트 `tools/build-fun/make-og.js`를 둬요. 나중에 유형형 결과별 이미지(manager 8, fan 8, club 12 = 28장)도 같은 스크립트로 한 번에 뽑을 수 있어요.
  - **주의: 작업 환경은 외부 네트워크가 막혀 있어서 Google Fonts(Black Han Sans)가 안 불러와져요.** 환경에 설치된 `Noto Sans CJK KR`(Black 굵기 있음)로 그려야 해요. 아니면 폰트 파일(OFL 라이선스)을 `tools/build-fun/fonts/`에 넣고 로컬로 불러와요. 대체 폰트로 그리면 글자가 깨지지는 않지만 카드 본문 글꼴과 느낌이 달라져요.
  - 파일 크기는 PNG 300KB 이하 목표(카톡 미리보기 로딩).
- 메타: `og:image`(절대 URL `https://fifagosu.pages.dev/fun/og/default.png`), `og:image:width=1200`, `og:image:height=630`, `og:image:alt`, `twitter:card=summary_large_image`. Function이 결과 링크에서 바꾸는 건 title/description/url만 하고, 이미지는 기본 1장을 같이 써요.
- 참고: 본 사이트 `site/templates/base.html`이 쓰는 `site/brand/og-image.png`는 이 작업 폴더에 `site/brand/` 폴더 자체가 없어요(build.py는 이 폴더를 복사하려고 해요). 저장소에서 빠진 건지, 다른 곳에서 넣는 건지 확인이 필요해요. 킥킥 이미지는 `fun/og/`에 두면 이 문제와 상관없어요.

## 6. 그 밖의 위험 요소

1. **main 병합 = 자동 배포.** `news.yml`이 매일 06:50/11:50/17:50/21:50(한국 시간)에 main을 빌드해서 Cloudflare에 배포해요. **대표 배포 승인 전에는 main에 합치면 안 돼요.** QA는 작업 브랜치에서 하고, 미리보기 배포가 필요하면 `renewal` 브랜치 배포(crawl.yml이 main이 아니면 `--branch=renewal`로 배포)를 쓰거나 대표 승인 후 수동 실행해요. Function 동작(og 주입)은 로컬에서 확인할 수 없어서 **미리보기 배포에서만** 확인할 수 있어요.
2. **카톡 미리보기 캐시.** 카카오는 URL별로 미리보기를 캐시해요. 지금 `/fun/` 미리보기(이미지 없음)가 이미 캐시돼 있을 수 있어서, 배포 후 카카오 공유 디버거에서 캐시를 지워야 해요(카카오 개발자 로그인 필요, 아무 계정이나 가능).
3. **Function 보안.** 디코딩한 이름·별명을 meta에 넣을 때 길이 제한(이름 6자, 별명 24자)과 문자 검사를 해요. `HTMLRewriter`의 `setAttribute`는 따옴표를 처리해 주지만 그래도 검증이 먼저예요. 디코딩 실패 시에는 기본 메타를 그대로 내보내요.
4. **질문·문구 수정 시 옛 링크 결과가 바뀌는 문제.** 결과는 "현재 데이터 + 이름 + 답변"으로 다시 계산하기 때문에, 질문표나 태그를 고치면 같은 링크가 다른 별명을 보여줄 수 있어요. → `v1` 버전 표시(2-3)로 대응하고, **배포 후에는 문항 순서와 선택지 순서를 바꾸지 않는 규칙**을 정해요.
5. **인앱 브라우저.** 카톡·인스타 인앱 브라우저에서 `navigator.share`(파일)와 `clipboard`가 실패하는 경우가 많아요. 복사 실패 대비책(입력창)과 "이미지를 길게 눌러 저장" 안내는 QA 필수 항목이에요.
6. **이름이 링크와 미리보기에 노출.** 초안의 "닉네임도 OK" 안내는 유지하고, 결과 링크 복사 버튼 옆에 "링크에 이름이 포함돼요" 작은 문구를 둬요.
7. **문구 검수 병목.** 이름 생성기 문구(합성 단어 약 60개 + 수식어 24개 + 근거 16개 + 반전 6개 + 등번호 8개 ≈ 110~120개)는 개발자가 쓰면 다시 "억지" 평가를 받을 위험이 있어요. **문구는 오후 중간에 대표님께 한 번 보여 드리고 확정**하는 체크포인트를 일정에 넣는 걸 추천해요.
8. **캔버스 메모리.** 결과 링크로 바로 결과를 그릴 때도 1080×1920 캔버스를 `toDataURL`로 넣고 있어요. 저사양 폰을 위해 `toBlob` + `createObjectURL`로 바꾸는 건 10분짜리라 같이 하는 걸 추천해요.
